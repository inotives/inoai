# Fail closed when a Discord approval cannot be explained safely

Codex app-server requests may contain arbitrary text and optional action, network, and permission fields. Copying an unreviewed request to SQLite or Discord could leak credentials; a generic Approve button would not give informed consent. CLI `0.164.0` exposes a full `command` and `cwd` for some `item/commandExecution/requestApproval` requests. For this narrow shape, inoai shows the exact command and working directory in a Discord card and accepts only the configured owner's one-time click on the same live request. The card expires after 15 minutes. The request must be a regular `command` with a local environment, no separate approval callback, and no network, added-permission, or policy-amendment fields. Parsed `commandActions` are best-effort display metadata; the full `command` is the preview authority. If the command or working directory is missing, malformed, secret-like, unsafe to render, or too long for Discord, inoai declines it. It also declines file changes, terminal input, generic permission requests, and unknown shapes, then sends a fixed notice to use local Codex. SQLite keeps only a fixed summary, generic card record, and outcome; it never stores the command or working directory. A restart fails pending cards and cannot resume the lost live request. This does not change Codex's configured sandbox or approval policy and adds no wrapper command allowlist.
