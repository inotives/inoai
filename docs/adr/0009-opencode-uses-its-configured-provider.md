# OpenCode uses whatever provider and model it is configured with

The OpenCode adapter drives the owner's installed `opencode run --format json --standalone` once per Turn and passes no model or provider selection, so each Turn uses OpenCode's own configured default. Today that is a free OpenCode Zen model, which bills nobody but sends Discord prompts and project context to opencode.ai. Unlike the Codex and Claude adapters, inoai adds no credential or model guard: the owner accepted that any reply from OpenCode is acceptable and that a paid provider or API key the owner later configures in OpenCode will be used as configured. inoai still never edits OpenCode configuration, never passes `--auto`/`--yolo`/`--dangerously-skip-permissions`, and documents the data flow and billing consequence in the README. Revisit with a guard if the owner wants subscription-only providers (for example GitHub Copilot or ChatGPT sign-in).

The same rule covers permissions: inoai keeps OpenCode's configured permission policy and never tightens or loosens it. The live smoke test showed that OpenCode's built-in defaults allow shell and most tools and ask only in a few cases, so a default install lets an owner-only Discord message run commands in the deployment folder; only `ask` cases are auto-rejected with the fail-closed notice. The owner accepted this and may tighten their own OpenCode configuration; a startup guard that refuses permissive effective rules is a possible follow-up, deferred because it depends on version-specific `debug config` output.
