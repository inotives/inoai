## Blocker

Task 0078 cannot safely wire PostgreSQL into normal startup yet. Tasks 0075 and
0076 delivered the asynchronous `PostgresOperationalStore` and PostgreSQL
Manual Memory adapter, but the active runtime consumers still require the
synchronous SQLite API:

- `ConversationWorker`
- `startTransport` and inbound classification in `index.ts`
- `agent-session.ts`
- `runtime-turn.ts`
- `prompt-context.ts`
- `memory-review-scheduler.ts`
- `approval-relay.ts`
- provider permission-denial notifiers

Starting with a PostgreSQL pool while leaving these consumers on
`DatabaseSync` would either fail type/runtime checks or silently preserve the
SQLite operational path, violating the task acceptance criteria that Discord,
the conversation worker, Memory Review, and Manual Memory all use PostgreSQL
and that startup not create or consult SQLite.

## Evidence

`rg -n "DatabaseSync|openDatabase|instance\\.database|MemoryReviewScheduler|ConversationWorker" src`
shows the above runtime modules still importing `node:sqlite` or calling the
SQLite `database.ts` helpers. The async store interface has the required
operations, but no consumer adapter or async equivalents are wired.

## Recommendation

Create a prerequisite consumer-migration task (or expand task 0075) to port
the worker, transport policy, runtime-turn/session helpers, prompt context,
review scheduler, and approval relay to an async `OperationalStore` boundary.
Then resume 0078 to perform startup pool/lease lifecycle wiring and remove the
remaining SQLite runtime calls. Keep the existing SQLite modules only for
Electron Phase 7 and legacy/unit-test coverage until that migration is
complete.
