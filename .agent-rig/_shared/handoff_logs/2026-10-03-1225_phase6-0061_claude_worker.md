## Design decisions

- **Timing:**
  - The due check runs at startup and every 60 s, which also covers sleep and wake.
  - A cycle is due when `now >= today HH:MM` and no `memory_review_cycle` Event with `date=<local date>;` exists.
  - Scheduling fields (`next_attempt_at`, `started_at`) use the injected clock; audit columns use SQLite time.
- **Cycle:**
  - Runs in one transaction.
  - No `review` method: one `memory_review_skipped` Event (`date=D; reason=unsupported_runtime`) and no rows.
  - Otherwise, each non-deleted Session (active or ended) gets at most one open row. The range runs from the first Message after the completed cursor (any state) through the last settled Message before the first pending or processing one. The Session is skipped unless that range holds a completed Message.
  - An existing pending or failed row with the same range is re-armed in place: `attempts=0`, `next_attempt_at=now`, still `pending`. This avoids duplicates and gives a failed row a fresh day of retries.
  - A changed range retires the old row (`failed`, `failure_detail='stale_range'`, soft-deleted) and inserts a replacement. If nothing is left to review, the row is retired.
  - A cycle never runs while a review is active; the next poke after the review settles picks it up.
- **Runner:**
  - Claims the oldest due `pending` row, only when the runtime has `review` and no user Message is `processing`, or `pending` in an active Session.
  - A stranded pending Message in an ended Session can never be claimed by the worker, so it must not starve reviews.
  - One review at a time. `reviewSession` gets `{ reviewId, maxChars, signal }`.
- **Preemption hook:** `ConversationWorker.wake()` is the single path every inbound archive (top-level, bound thread, reset thread) and every Turn transition goes through. A narrow listener there needs no change to transport code, and the scheduler re-reads queue state from SQLite rather than trusting the event. When chat work exists during a review, `poke()` aborts with reason `preempted`. After chat settles, the worker's `wake()` pokes again and the review restarts.
- **Results:**

| Result | Handling |
| --- | --- |
| `completed` | If `throughMessageId` is short of the row's through (the window cap), insert a follow-up row from the next Message to the original end. It runs next, in the same cycle. |
| `empty` | Complete the row with `recap=NULL` and write a `memory_review_completed` Event (`…; empty=1`). The cursor moves past notices and failed Messages, so no row stays pending forever. Recap lookups already filter `recap IS NOT NULL`. |
| aborted, reason `preempted` | Back to `pending`, attempts unchanged, `memory_review_deferred` Event `review=ID; date=D; deferrals=N` (counted from Events for that row and local date). On the 5th, `next_attempt_at` is set to the next scheduled time, and the next cycle re-arms the row. |
| aborted, reason `shutdown` | Back to `pending`, no Event. |
| `stale_range` | Re-derive the range and replace the row in one transaction. If the re-derived range equals the row's, it counts as a failed attempt, so it cannot loop. |
| `failed` | `attempts+1`, `failure_detail` = reason code, retry at +1h/+2h/+4h, then `failed` after the 4th failure until the next cycle re-arms the row. |
| thrown error | The engine has already rolled back, so it is recorded as `failed` with reason `commit_error`. |

- **Restart:** the existing `recoverStaleWork` sets `processing` rows back to `pending` with attempts untouched; a test covers this.
- **Silence:** the scheduler holds no transport.

## Residuals and notes for the reviewer

- Wiring in `run()` uses the real clock. In the existing `run()` tests, the startup cycle runs before any Session exists (`enqueued=0`), or is skipped for Codex and OpenCode. This depends on the wall clock: before 06:00 no cycle Event is written. No test asserts the full Events list.
- A review may overlap a just-claimed chat Turn for the moment it takes to abort. Chat is never delayed; the review is cancelled.
- A Session whose open row is `processing` when a cycle would run is skipped by the cycle. In practice this cannot happen: the cycle waits for the active review to settle, and restart recovery clears stale `processing` rows first.
- A follow-up row covers only the remainder up to the original row's end. Newer Messages wait for the next cycle.
