## Design

- **Range.** The range is the Messages after the Session's completed cursor. It stops before the first `pending`/`processing` Message; with `reviewId`, an unsettled Message inside the range gives `range_not_ready`. Content is the completed owner-authored user Messages plus completed agent Messages, minus fixed notices matched by exact text. The cursor (`through_message_id`) also covers trailing notices and failed Messages.
- **Windows.** A window holds at most `max(maxChars, 500)` characters. Each Message is labelled `[message N] owner|agent:`. An oversized Message is split into `[message N, part i/n]` parts. At most 60 windows are built; past that, the range ends at the last whole Message and the rest waits for the next review.
- **Notes.** One `runtime.review` call per window, which must reply `{"notes": string}`. Notes are capped at `clamp(12000/windows, 200, 2000)` characters, redacted, and held in memory only.
- **Aggregation.** One final call with the notes, active Memory (`[memory id] origin=…: body`, 6,000-char budget) and recent agent-wide completed Recaps (`[recap id] …`, 6,000-char budget). The prompts are fixed templates in code. They mark data with tags, contain no tool wording, and ask for JSON only.
- **Recap.** It must be a non-empty string; a secret-like recap fails the attempt (`unsafe_recap`). A recap over 1,500 characters is truncated.
- **Validation and reason codes:**
  - `model_ignore`, `invalid_action`, `too_many_actions` (more than 20 actions)
  - `unknown_memory`, `manual_entry`, `duplicate_target`
  - `source_out_of_range`, `unknown_recap`
  - `missing_body`, `body_too_long` (over 500 characters), `secret_like`, `missing_source`
  - `no_memory_signal`. For add/update, the signal is either an explicit one (a cited in-range owner Message whose text contains a remember-style phrase once quotes, fences, inline code, and `>` lines are removed) or a recurrence (≥ 2 distinct prior completed Recap IDs).
  - `no_evidence`. A delete needs a cited owner Message or ≥ 2 prior Recaps.
  - A `memory_id` on `add` is ignored.
- **Commit.** Everything is written in one `BEGIN IMMEDIATE`:
  1. Re-check the cursor and the review row (`stale_range` if either changed).
  2. Create the row if none was given, or use the given one; shorten `through` if the window cap applied.
  3. Run `completeMemoryReview` with actor `memory-review`.
  4. Validate against the database inside the transaction.
  5. Apply the changes. An add creates a Memory with `origin='review'`, `review_id`, `source_message_id`, and `created_by_user_id=null`. An update soft-deletes the old entry and inserts a replacement. A delete is a soft-delete.
  6. Write one `memory_review_completed` Event with counts and `reasons=code:n,…`.
  7. `COMMIT`. Any error triggers a rollback.
- **Ignored outcomes** go in that Event, so no schema change is needed (`docs/sqlite-schema.md` already routes review bookkeeping through Events). Model reason text is never stored.

## Residual risks

- Notices are matched by exact text for the current runtime's display name, plus all known permission and mismatch variants. A home whose provider changed can keep old runtime-failure notices worded for the previous provider; those would be reviewed as agent text.
- The 500-character window floor and the 60-window cap are engine constants, not config.
- The `delete` evidence rule goes beyond the literal task text. It is conservative, and the reviewer should confirm it.
