# Task 0020 worker handoff

The default inbound handler now applies the accepted eligibility policy, creates a Discord thread for each new top-level owner mention, and stores its active Session and pending initiating user Message in one SQLite transaction. It binds the thread ID, initiating Discord message ID, configured provider, and deployment-folder project path. No Agent Runtime is called.

An in-flight message-ID guard prevents simultaneous duplicate deliveries from creating extra threads. The persisted initiating-message uniqueness key prevents later deliveries from creating another Session or Message. A second distinct request creates a separate thread and Session.

Changed files: `src/index.ts`, `src/test/transport.test.ts`. The test uses a fake Discord client and an isolated temporary runtime home; it covers two requests plus concurrent and later duplicate delivery.

Verification: `npm test` (42 passing), `npm run typecheck`, `npm run build`, and `git diff --check` passed. No live Discord connection, credentials, commit, or push.

Review focus: Discord thread creation happens before the SQLite transaction. If persistence fails after Discord succeeds, an orphan thread can remain; there is no cross-system atomic operation in the current transport API. Normal duplicate delivery after persistence is idempotent.
