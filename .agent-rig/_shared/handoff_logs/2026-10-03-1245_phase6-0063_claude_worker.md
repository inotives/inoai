## Why the pnpm Memory was missed (defect, not fixed here)

The window reply was:

```
{"notes": "Owner prefers pnpm over npm for this project [message 1]."}
```

It kept the preference but dropped the fact that message 1 was an explicit remember request. The window prompt asks for that, but the instruction is soft.

The aggregation prompt sees only the notes, not the transcript. Its rule says to add only when an owner message "explicitly asks to remember". The model therefore answered `op: "ignore"` with the reason "no explicit request to remember". The deterministic validator (`hasMemorySignal` on message 1, "Please remember that…") would have accepted an `add` that cited message 1. The fault is in what the two-step design passes between steps: the explicit-signal evidence is lost on the way from the window step to the aggregation step.

Candidate fixes need a planner/owner decision:

- (a) The engine computes owner Message IDs that pass `hasMemorySignal` and lists them in the aggregation prompt as "explicit remember requests" (deterministic, no new trust in the model).
- (b) Make the window notes reply structured, e.g. `{"notes", "explicit_requests": [ids]}`, and re-validate the IDs.
- (c) Include the signalled owner Message text in the aggregation step.

Option (a) looks smallest. Any fix needs regression coverage in `src/test/memory-review.test.ts` and then a re-run of this task. This is one `haiku` sample. Another model might behave differently, but the structural gap stays.
